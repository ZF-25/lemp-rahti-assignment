Part A - Theory Questions

1. Explain the difference between Continuous Integration, Continuous Delivery and Continuous Deployment.

Continuous Integration (CI) is the process of regularly combining code changes into a shared repository and automatically checking that the changes do not break the project. The idea is that instead of waiting until the end of a project to find problems, developers get feedback soon after making changes. For example, a CI pipeline could build the Docker image and run tests whenever new code is pushed to GitHub.

Continuous Delivery goes one step further. The application is automatically built, tested and prepared so that it is always in a state where it could be released. The final release can still require a person to approve it. So the software is ready for deployment, but the actual deployment does not necessarily happen automatically.

Continuous Deployment goes one step further again. When the code passes the required automated checks, it is automatically deployed without someone having to manually approve every release. This means that a successful change can go from the repository to the running application as part of the same automated process.

I think the easiest way to remember the difference is that Continuous Integration is about checking changes, Continuous Delivery is about keeping software ready to release, and Continuous Deployment is about automatically releasing it.

In my Week 6 project, I implemented a pipeline that is closest to Continuous Deployment for the week6 branch. When I pushed my changes, GitHub Actions automatically built the backend Docker image, pushed it to Docker Hub, logged into Rahti, updated the backend Deployment and waited for the rollout to complete.

This was useful because I did not have to manually build the image and then manually update the Deployment every time. The pipeline connected these steps together.

Source: Atlassian documentation on Continuous Integration, Continuous Delivery and Continuous Deployment.

2. Describe the structure of a GitHub Actions workflow (triggers, jobs, steps). What would a minimal pipeline for the app you built in Week 4/5 need to do?

A GitHub Actions workflow is a YAML file that describes what should happen automatically when something happens in a GitHub repository. The workflow normally contains a trigger, jobs and steps.

The trigger decides when the workflow should start. For example, it can run when code is pushed to a particular branch. In my Week 6 project, I used a push trigger for the week6 branch, so pushing new changes to that branch starts the workflow.

A job is a group of related tasks that runs on a GitHub Actions runner. My workflow has one job called build-push-deploy. Inside that job I have several steps that are executed in order.

The steps are the individual actions or commands that make up the job. In my workflow, the first step checks out the repository so the runner has the project files. The next steps log into Docker Hub, build the backend Docker image and push it to Docker Hub. After that, the workflow installs the OpenShift CLI and logs into the Rahti project. Finally, it updates the backend Deployment and waits for the rollout to finish.

A minimal pipeline for the guestbook application would therefore need to do something like this:

  1. Get the latest code from the GitHub repository.
  2. Build the backend Docker image.
  3. Run some basic checks or tests before deployment.
  4. Push the image to a container registry.
  5. Log into the Rahti/OpenShift project using a stored secret.
  6. Update the backend Deployment to use the new image.
  7. Wait for the deployment rollout and make sure it becomes healthy.

My Week 6 workflow follows this same basic process. I used the Git commit SHA as the Docker image tag. This means that the image deployed to Rahti can be connected back to the exact commit that triggered the workflow. For example, instead of always deploying an image called latest, the workflow produced an image with a tag based on the commit SHA. 

on:
  push:
    branches:
      - week6

jobs:
  build-push-deploy:
    runs-on: ubuntu-latest

One thing I learned from this is that a CI/CD pipeline is not just a GitHub Actions file that turns green. For this assignment, the important part was that the workflow actually changed the running application in Rahti. That is why I also checked the deployed image and the final public application after the workflow completed.

Source: GitHub Actions documentation on workflows, jobs and steps.

3. What are the three pillars of observability (metrics, logs, traces)? Give an example of a question each is best suited to answer.

The three main pillars of observability are metrics, logs and traces. They give different types of information about what is happening inside an application. They are related, but each one is useful for answering different questions.

Metrics are numerical measurements collected over time. Examples include CPU usage, memory usage, request count, response time or error rate. Metrics are useful when I want to see the overall state or behaviour of an application.

For example, a question that metrics could answer is: "Has the error rate of my backend increased during the last 30 minutes?" A graph showing the HTTP error rate over time would make it easier to notice a change compared with looking at individual requests.

Logs are records of events that happened in the application. They can contain details about individual requests, errors, warnings and other events. Logs are especially useful when I need to find out what happened at a particular moment.

For example, a question that logs could answer is: "Which endpoint returned an HTTP 500 error?" In my Week 6 project, I added structured JSON request logging to the Flask backend. Each request can include the HTTP method, path, response status and request duration. 

{
  "event": "http_request",
  "method": "GET",
  "path": "/healthz",
  "status": 200,
  "duration_ms": 0.08
}

I could then use oc logs to retrieve these records from the backend pod. This made the logging part of observability something I could actually test instead of only reading about it.

Traces are used to follow a request as it moves through different parts of an application. This becomes especially useful when an application has several services and it is not immediately obvious which part is causing a delay.

For example, a tracing system could answer: "Why did this particular request take two seconds to complete, and which service caused most of the delay?" A trace could show the time spent in the frontend, backend and database separately.

Observability pillar What it tells me Example question
Metrics Numerical values and trends over time. Has the backend error rate increased?
Logs Specific events and details from the application. Which request or endpoint produced an error?
Traces The path and timing of a request through multiple services. Which part of the application made this request slow?

For this assignment I mainly implemented logging and health checks rather than setting up a complete metrics and tracing system. Even though the project is small, adding structured logs was useful because I could retrieve information from the actual running backend with oc logs.

Source: OpenTelemetry documentation on observability signals.

4. Explain the difference between a liveness probe and a readiness probe in Kubernetes/Rahti. What happens when each fails?

A liveness probe and a readiness probe are both health checks, but they answer different questions. The easiest way I understand the difference is that liveness asks whether the application is still alive, while readiness asks whether the application is ready to receive traffic.

A liveness probe is used to check whether a container is still functioning. In my application, the liveness probe calls the /healthz endpoint. This endpoint simply returns a successful response when the Flask application is responding. 

livenessProbe:
  httpGet:
    path: /healthz
    port: 8000
  initialDelaySeconds: 10
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3

If the liveness probe repeatedly fails, Kubernetes can treat the container as unhealthy and restart it. This is useful for situations where the application is stuck or has reached a state where restarting the container may recover it.

A readiness probe is different. It checks whether the application is ready to receive normal traffic. In my project, the readiness endpoint is /readyz. It tries to connect to MySQL and only returns a successful response when the backend can access the database. 

readinessProbe:
  httpGet:
    path: /readyz
    port: 8000
  initialDelaySeconds: 10
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3

If the readiness probe fails, Kubernetes does not consider the pod ready for normal Service traffic. Importantly, the container does not necessarily get restarted just because it failed the readiness check. The application can still be running but temporarily unable to serve requests correctly.

I actually tested this part instead of only putting the probes in the YAML file. I temporarily changed the readiness probe from /readyz to a path that did not exist: 

readinessProbe:
  httpGet:
    path: /not-a-real-endpoint
    port: 8000

After applying the change, the new backend pod was still shown as Running, but it was 0/1 ready. This was a useful test because it showed the difference between liveness and readiness in practice. The container itself was still running, but Kubernetes did not consider it ready to receive normal traffic.

I then restored the correct /readyz endpoint. After the probe was fixed, I also restored the SHA-tagged backend image and waited for the rollout to complete. The backend became healthy again.

Probe Main question My Week 6 endpoint What happens if it fails?
Liveness Is the container/application still alive? /healthz Repeated failure can cause the container to be restarted.
Readiness Is the pod ready to receive traffic? /readyz The pod is marked not ready and is removed from normal Service traffic until it becomes ready again.

This was probably the part of Week 6 that made the most sense to me after actually testing it. Before the practical work, I mostly thought of both probes as general health checks. After deliberately breaking the readiness endpoint and seeing 0/1 while the pod was still running, the difference became much clearer.

Source: Kubernetes documentation on liveness, readiness and startup probes.

2. Checking the existing Rahti application

Before changing anything, I checked the existing application and backend deployment in Rahti. This was useful because I wanted to make sure the Week 6 work was being added to the existing project rather than accidentally creating a different application.

3. Adding the liveness and readiness endpoints

I added two simple endpoints to backend/app.py. The liveness endpoint is intentionally simple because its job is to show that the Flask application itself is responding. The readiness endpoint is a little more useful because it checks the MySQL connection before returning that the backend is ready. 

# Kubernetes liveness probe
@app.get("/healthz")
def healthz():
    return jsonify({"status": "ok"}), 200

# Kubernetes readiness probe
@app.get("/readyz")
def readyz():
    try:
        conn = get_db_connection()
        conn.close()
        return jsonify({"status": "ready"}), 200
    except Exception:
        return jsonify({"status": "not ready"}), 503

I chose these endpoints because they make the two checks easy to test from inside the backend container and easy for Kubernetes to call.

4. Testing the health endpoints

I tested the liveness endpoint and received HTTP 200 with the expected JSON response.

I also tested the readiness endpoint. When the backend was connected to the working MySQL deployment in Rahti, it returned HTTP 200 and {"status":"ready"}.

5. Configuring the probes in the backend Deployment

I added both probes to k8s/backend-deployment.yaml. Both checks use HTTP on port 8000. The liveness probe calls /healthz and the readiness probe calls /readyz. 

livenessProbe:
  httpGet:
    path: /healthz
    port: 8000
  initialDelaySeconds: 10
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /readyz
    port: 8000
  initialDelaySeconds: 10
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3

I then checked the running pod and confirmed that the probes were actually present on the deployed container rather than only existing in the YAML file.

6. Deliberately failing the readiness probe

The assignment specifically asked for the readiness check to be deliberately failed. To test this, I temporarily changed the readiness path from /readyz to a path that does not exist. 

readinessProbe:
  httpGet:
    path: /not-a-real-endpoint
    port: 8000

After applying this temporary change, a new backend pod was created. The pod was still Running, but it was not ready, so it showed 0/1. This was exactly the behaviour I wanted to demonstrate: a readiness failure keeps the pod from being treated as ready for normal Service traffic, rather than automatically treating the container as dead.

After taking the screenshot, I restored the correct /readyz path. Applying the Deployment manifest reset the image field to the image written in the manifest, so I then used oc set image to put the CI/CD image back on the Deployment and waited for the rollout to complete.

Result: The deliberate failure was temporary. I restored the working /readyz probe and confirmed that the backend became healthy again.

7. Adding structured logging

I also added a small amount of structured logging to the Flask backend. The goal was to make each HTTP request easier to inspect. Instead of only printing a normal text message, the backend writes JSON containing the event name, HTTP method, request path, response status and request duration. 

logging.basicConfig(
    level=logging.INFO,
    format="%(message)s"
)
logger = logging.getLogger(__name__)

@app.before_request
def start_request_timer():
    request.start_time = time.perf_counter()

@app.after_request
def log_request(response):
    duration_ms = round(
        (time.perf_counter() - request.start_time) * 1000,
        2
    )
    logger.info(json.dumps({
        "event": "http_request",
        "method": request.method,
        "path": request.path,
        "status": response.status_code,
        "duration_ms": duration_ms
    }))
    return response

This means that a request such as GET /healthz produces a log entry containing information like the request path and status code. It is useful because I can retrieve the logs with oc logs without needing to change the application code again just to investigate a request.

8. Retrieving the structured logs from Rahti

I used oc logs on the running backend pod and could see the JSON request records. The logs included successful calls to both /healthz and /readyz.

A simplified example of the output is:

{"event": "http_request", "method": "GET", "path": "/healthz", "status": 200, "duration_ms": 0.08}
{"event": "http_request", "method": "GET", "path": "/readyz", "status": 200, "duration_ms": 1.23}

I found this more useful than a plain message because the fields have a consistent structure. For a larger application, these fields could be collected by a logging system and searched or used as part of an alert.

Before relying on the GitHub Actions deployment, I also tested the backend locally. I rebuilt the backend image with Docker Compose and checked that the Python application could be compiled. I also tested the new endpoints. 

docker compose -f docker-compose.dev.yml build backend

10. Creating the GitHub Actions CI/CD workflow

I created .github/workflows/week6-cicd.yml. The workflow is triggered when code is pushed to the week6 branch. I used the separate Week 6 branch so the protected Week 5/main version stayed unchanged. 

name: Week 6 CI/CD

on:
  push:
    branches:
      - week6

jobs:
  build-push-deploy:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Log in to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build backend image
        run: |
          docker build \
            -f backend/Dockerfile \
            -t ${{ secrets.DOCKERHUB_USERNAME }}/lemp-rahti-backend:${{ github.sha }} \
            .

      - name: Push backend image
        run: |
          docker push \
            ${{ secrets.DOCKERHUB_USERNAME }}/lemp-rahti-backend:${{ github.sha }}

      - name: Install OpenShift CLI
        uses: redhat-actions/oc-installer@v1

      - name: Log in to Rahti
        uses: redhat-actions/oc-login@v1
        with:
          openshift_server_url: https://api.2.rahti.csc.fi:6443
          openshift_token: ${{ secrets.RAHTI_TOKEN }}
          namespace: cloud-services-assignment4

      - name: Apply backend configuration and deploy image
        run: |
          oc apply -f k8s/backend-deployment.yaml

          oc set image deployment/backend \
            backend=${{ secrets.DOCKERHUB_USERNAME }}/lemp-rahti-backend:${{ github.sha }}

          oc rollout status deployment/backend --timeout=180s

The image tag uses ${{ github.sha }}. This means each workflow run produces a traceable image tag based on the exact Git commit that triggered the workflow. This is better for this assignment than always using a tag such as latest, because I can see which commit produced the deployed image.

17. Alerting and a realistic alert rule

I did not install a full Prometheus/Grafana alerting system as part of this week's practical work. However, I did create structured logs and tested the health checks, so I now have useful signals that could be used for alerting.

Based on the logs and health checks I collected, one practical alert for this application would be:

Example alert: Alert if the backend returns HTTP 5xx responses for more than 5% of requests for five minutes, or if the backend Deployment has no ready pod for several minutes.

I would not alert on every individual GET /healthz request or every short delay, because that would create unnecessary notifications. The readiness failure test also showed why an alert about "no ready backend" could be useful: the pod can still be running while not being able to receive normal application traffic.

For a real production setup, I would connect these signals to a monitoring/alerting system and tune the thresholds after observing normal traffic. For this student project, keeping the number of alerts small makes more sense than trying to monitor every possible metric.
